# 孤兒檔對帳（blob-reconcile）

把 Blob 容器裡的檔案與資料庫的引用對一次，列出「沒有任何欄位指得到」的檔案。

## 🔴 只能對正式資料庫跑

儲存體帳戶只有一個（`st20skinweb`），**所有環境共用同一個容器**。
所以「這個檔案還有沒有人在用」只有正式資料庫答得準。

2026-09-16 實測，對錯的資料庫跑會發生什麼：

| 對誰跑 | 結果 |
|---|---|
| 空的測試庫 `Skin20_WriteTest` | **4613 / 4616（100%）**被報成孤兒 |
| 本機開發庫 `20skin-website` | **3439 / 4616（75%）**被報成孤兒 |

兩次都不是資料有問題，是問錯了資料庫。**加上刪除旗標就是把整站圖片清光。**

因此工具內建比例安全閥：孤兒檔超過容器的 20% 時**拒絕刪除**，除非明確加 `--force`。

## 用法

```bash
# 只報告（預設）
SKIN20_EXPORT_SQL='<正式庫的唯讀連線字串>' \
  dotnet run --project tools/blob-reconcile

# 確認清單無誤後才刪
SKIN20_EXPORT_SQL='…' dotnet run --project tools/blob-reconcile -- --delete
```

| 參數 | 預設 | 說明 |
|---|---|---|
| `--account` | `st20skinweb` | 儲存體帳戶。🔴 `st20skinprod` 是**預約系統**的，不要打錯 |
| `--container` | `media` | 容器 |
| `--min-age-hours` | `24` | **保護期**。比這個新的檔案一律略過 |
| `--delete` | 關 | 真的刪檔 |
| `--force` | 關 | 略過比例安全閥 |

⚠️ **保護期不可設 0 去跑刪除。** 對帳跑的當下可能正好有人上傳完、還沒按儲存 ——
那個檔案在資料庫裡本來就還不該有引用。刪掉它，編輯按下儲存時就會存進一個指向 404
的網址，而且沒有任何錯誤訊息。

## 孤兒檔從哪裡來（都不是 bug）

1. **上傳了但沒存檔** —— `/admin/upload/commit` 成功後，編輯關掉視窗沒按儲存。
2. **清檔逾時或失敗** —— 換圖時刪舊檔有時間上限（存檔不該為了清檔而變慢），
   逾時就放掉並記一行 warning（`換圖後刪除舊檔失敗，留下孤兒檔`）。
3. **換圖之後、重新發布之前** —— 舊圖仍被「已發布快照」需要，所以刻意不刪
   （不然線上會破圖，見 docs/11 §9）。那筆內容重新發布時才會清掉。

## 參照集合怎麼算

🔴 **不硬寫欄位清單。** 規格原本描述成「要掃十個內嵌圖片欄位」——
那種寫法在有人新增第十一個欄位的那天就會默默漏掉，而症狀是
「對帳工具把還在用的圖片報成孤兒」，照著刪就是線上破圖。改成問 schema：

1. `INFORMATION_SCHEMA` 裡所有叫 `*BlobPath` 的欄位（新增欄位自動涵蓋）
2. 所有 `nvarchar(max)` 欄位裡的 JSON，掃 `blobPath` 這個鍵（BodyBlocks、首頁版位設定…）
3. **已發布版本的快照** —— 前台服務的是已核准快照，不是工作副本（CLAUDE.md 決策 14）

⚠️ 第 3 點只取「已發布的那一版」。舊版本本來就允許指向已刪除的圖片
（docs/11 §9：版本還原救不回已刪除的圖片），全算進來等於永遠不能清。
